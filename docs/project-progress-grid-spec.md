# 專案進度百分比與階段／任務 grid 規格

狀態：ready-for-agent，2026-10-20。依 grill 訪談（Q1–Q12）的共識撰寫。詞彙以 [CONTEXT.md](../CONTEXT.md) 為準，新增詞彙為「進度」「專案整體進度」。版面參考原型 `proto-types/weekly-report-ui.html` 的「編輯時程」表格。

## Problem Statement

課長在專案編輯畫面維護階段與關鍵任務時，遇到三個問題：

1. 狀態為「進行中」的階段或任務看不出做到哪裡，專案標頭只有「完成 x/y」，無法呈現進行中項目的進度。
2. 時程明細是逐項展開的兩列卡片，項目一多就很長；甘特圖又排在明細之下，編輯時看不到全貌，無法一邊看時程圖一邊對照明細。
3. 要在某個階段底下新增任務，只能用專案層級的「新增關鍵任務」，再自己從「所屬階段」下拉選階段，新任務也不會出現在該階段附近。

## Solution

階段與關鍵任務新增「進度」（0–100%）。進行中的任務由課長手動填寫，進行中的階段若有子任務則由子任務推算。進度顯示於 grid、甘特圖實際條旁、發布文件與專案標頭的「專案整體進度」。

編輯畫面改為甘特圖在上、時程 grid 在下：grid 為表格，有固定最大高度與自己的捲軸，表頭固定，欄位含進度。階段列提供「＋任務」，在該階段底下新增任務。grid 與甘特圖同順序、共用階段展開狀態，並可互相點選對照。

## User Stories

1. 身為課長，我想為進行中的關鍵任務填寫 0–100 的進度，以便處會主管看得出做到幾成。
2. 身為課長，我想在任務狀態改為「完成」時自動視為 100%，以便不必重複填寫。
3. 身為課長，我想「開放」狀態的項目自動視為 0%，以便尚未開始的項目不會顯示進度。
4. 身為課長，我想只有「進行中」的項目才能輸入進度，以便狀態與進度不會互相矛盾。
5. 身為課長，我想進度輸入限制在 0–100 的整數，以便不會填出無意義的數字。
6. 身為課長，我想「進行中」卻尚未填進度的項目顯示「—」，以便分得出「尚未填寫」與「0%」。
7. 身為課長，我想狀態改成「進行中」時進度欄留空，以便系統不替我猜一個數字。
8. 身為課長，我想有子任務的階段進度自動由子任務推算，以便不必手動加總。
9. 身為課長，我想階段進度推算排除已取消的子任務，以便取消的項目不拖低進度。
10. 身為課長，我想沒有子任務的階段可以手動填進度，以便單純階段也能呈現進度。
11. 身為課長，我想子任務全部 100% 時階段狀態不會自動變成「完成」，以便階段完成仍由我確認。
12. 身為課長，我想階段標為「完成」時進度一律 100%，以便與我的確認一致。
13. 身為課長，我想里程碑與已取消項目不顯示進度，以便畫面不出現沒有意義的百分比。
14. 身為課長，我想在專案標頭看到專案整體進度，以便快速掌握整體狀況。
15. 身為課長，我想專案整體進度以階段與直接隸屬專案的任務各為一單位計算，以便階段底下的任務不被重複計入。
16. 身為課長，我想專案標頭同時保留「完成 x/y」，以便原本熟悉的摘要不消失。
17. 身為課長，我想編輯畫面中甘特圖排在時程 grid 上方，以便先看全貌再編輯細節。
18. 身為課長，我想時程 grid 是一列一個項目的表格，以便一眼比較多個項目的欄位。
19. 身為課長，我想 grid 有固定最大高度與自己的捲軸，以便項目很多時仍能同時看到甘特圖。
20. 身為課長，我想 grid 往下捲動時表頭固定，以便知道每一欄的意義。
21. 身為課長，我想在窄螢幕上 grid 可橫向捲動，以便欄位不會被擠壓到無法操作。
22. 身為課長，我想 grid 欄位包含類型、名稱、負責、狀態、進度、計畫起訖、實際起訖、前置項目與操作，以便所有可編輯內容都在同一列。
23. 身為課長，我想計畫起訖與實際起訖沿用現有的日期範圍選擇器，以便操作方式一致。
24. 身為課長，我想 grid 列順序與甘特圖一致（階段、其任務、直接隸屬任務、里程碑），以便兩邊逐項對得上。
25. 身為課長，我想已取消項目在 grid 以灰階顯示並留在原組內，以便找得到並「重新啟用」。
26. 身為課長，我想在階段列按「＋任務」就在該階段底下新增任務，以便不必再選所屬階段。
27. 身為課長，我想新任務自動帶入該階段、日期留空，以便我自己決定期間。
28. 身為課長，我想按下「＋任務」後該階段自動展開並把游標放在新任務的名稱欄，以便立刻輸入。
29. 身為課長，我想保留專案層級的「新增關鍵任務」，以便新增不屬於任何階段的任務。
30. 身為課長，我想在任務列的「所屬階段」下拉改變任務所屬階段，以便把任務移到別的階段。
31. 身為課長，我想在操作欄使用佐證連結、取消、重新啟用與刪除，以便既有功能不因改版消失。
32. 身為課長，我想點開 📎 時佐證面板展開在該列下方，以便不離開所在的位置。
33. 身為課長，我想編輯畫面的階段預設展開，以便一進來就能看到並編輯任務。
34. 身為課長，我想 grid 與甘特圖共用階段展開／收合狀態，以便兩邊顯示一致。
35. 身為課長，我想點甘特圖的列時 grid 捲到並高亮對應列，以便從圖找到要編輯的項目。
36. 身為課長，我想點 grid 的列時甘特圖高亮對應列，以便從明細看到該項目在時程上的位置。
37. 身為課長，我想甘特圖實際條旁標示進度百分比，以便不看 grid 也知道進度。
38. 身為部級主管，我想在正式發布的週報看到各階段與任務的進度，以便處週會時掌握專案狀況。
39. 身為部級主管，我想發布文件的版面維持現有收合預設，以便閱讀版面簡潔。
40. 身為部級主管，我想舊的發布版本沒有進度欄位時仍能正常顯示，以便歷史版本不壞。
41. 身為課長，我想一個頁面有多個專案時每個專案各有自己的甘特圖與 grid，以便專案之間不互相干擾。
42. 身為課長，我想前置項目的檢查與錯誤提示在 grid 中照常運作，以便排程規則不因改版而失效。
43. 身為課長，我想外部交付表維持在 grid 之下，以便原本的操作位置不變。

## Implementation Decisions

**資料契約**
- 階段與關鍵任務新增選填欄位 `progress`（0–100 整數）。里程碑不使用此欄位。
- 後端 API 對時程欄位沒有 schema 驗證，此變更只影響前端與週報 JSON，不需後端改動。
- 舊的發布快照與草稿沒有 `progress`，不遷移；缺值規則見下。
- 寫入 JSON 的欄位白名單（時程輸出清理）需納入 `progress`；推算值（階段進度、整體進度）屬衍生資料，不寫入 JSON。

**進度規則（純函式，與甘特模型、專案健康度並列）**
- 單一項目的有效進度：完成 → 100；開放 → 0；進行中 → 已填值，缺值時為「未填」。已取消與里程碑 → 無進度。
- 顯示規則：進行中且未填 → 「—」；其餘顯示整數百分比。
- 計算規則：未填視為 0。
- 階段進度：有未取消子任務 → 子任務有效進度的等權平均（四捨五入為整數）；沒有子任務 → 沿用階段自己的規則（可手動填）。階段狀態為完成時一律 100。階段狀態永遠由課長手動選，不因子任務而改變。
- 專案整體進度：以階段與「直接隸屬專案的任務」各為一單位，等權平均；里程碑與已取消項目不計；階段底下的任務已含在階段內，不重複計。沒有任何單位時顯示「—」。
- 輸入限制：0–100 的整數，超出範圍時夾回邊界，空白表示未填。
- 專案健康度摘要在原有「完成 x/y」旁並列專案整體進度。

**畫面**
- 編輯畫面每個專案區塊的順序：專案標頭（含健康度與整體進度）、甘特圖、時程 grid、外部交付。
- 時程 grid 為表格，欄位：類型、名稱（任務含「所屬階段」下拉）、負責、狀態、進度、計畫起訖、實際起訖、前置項目、操作。計畫與實際起訖沿用日期範圍選擇器，平時精簡顯示 `mm-dd~mm-dd`（跨年或非今年改 `yy-mm-dd~yy-mm-dd`，里程碑單日 `mm-dd`，空值 `—`，tooltip 顯示完整日期），點擊才展開選擇器；里程碑沿用單日模式。前置項目沿用精簡多選元件。
- grid 容器有最大高度（約 50% 視窗高度）、垂直與水平捲軸，表頭固定。窄螢幕維持表格並橫向捲動，不改為卡片。
- 取代現有的逐項卡片明細；既有欄位（名稱、所屬階段、負責、狀態、日期、前置項目、佐證、取消、重新啟用、刪除）全數保留，不得遺失。
- grid 列順序在顯示時依甘特圖分組排序（階段、其任務、直接隸屬任務、里程碑），不改動資料陣列順序。已取消項目留在原組內以灰階顯示，不受甘特圖「顯示已取消」開關影響。
- 階段列提供「＋任務」與收合箭頭。新任務帶入該階段的所屬階段、日期與進度留空、狀態為開放；加入後自動展開該階段並聚焦新任務的名稱欄。專案層級的「新增關鍵任務」保留，用於直接隸屬專案的任務。
- 甘特圖與 grid 共用階段展開狀態（展開狀態需由兩者共同的上層持有）。編輯畫面預設展開；唯讀的發布文件維持現有收合預設。
- 對照：點甘特圖的列 → grid 捲到並高亮對應列；點 grid 的列 → 甘特圖高亮對應列。不做逐列同步捲動。
- 甘特圖實際條旁標示進度百分比；進行中未填顯示「—」。發布文件使用同一甘特元件，唯讀顯示進度，不顯示 grid。
- 操作欄的佐證（旁帶數量）、＋任務、取消、重新啟用、刪除皆為無文字 icon 按鈕（內嵌 SVG），說明以 `title` 與 `aria-label` 提供；專案層級的新增按鈕維持文字。
- 佐證面板展開在該列下方。外部交付表位置與行為不變。

## Testing Decisions

- 好的測試只驗證外部行為（輸入資料 → 顯示結果／畫面可見行為），不驗證元件內部狀態或實作細節。
- **接縫一：純函式單元測試**（優先、先寫，走 tdd）。涵蓋：單一項目有效進度與顯示規則、狀態聯動（完成 100、開放 0）、階段推算（排除取消、無子任務時手動、完成時 100、等權平均與四捨五入）、專案整體進度（階段與直接隸屬任務各一單位、里程碑與取消不計、無單位時「—」）、缺值處理、0–100 夾限、健康度摘要文字。事前例：既有甘特模型與專案健康度的測試。
- **接縫二：瀏覽器煙霧測試**（既有煙霧測試擴充，使用固定日期與 fixtures）。涵蓋：在階段下新增任務（位置在該階段底下、所屬階段正確、日期留空、階段展開、名稱欄取得焦點）；進度輸入與顯示（進行中可填、其他狀態不可填、缺值顯示「—」）；grid 有捲軸且表頭固定；甘特圖在 grid 之上；點列對照高亮；既有功能（佐證、取消、重新啟用、刪除、前置項目錯誤）不退化。
- 前置項目規則本身沒有變動，既有排程規則測試維持原樣，不新增。
- 不新增第三種接縫；元件不另寫單元測試。

## Out of Scope

- 依天數加權的進度推算。
- 子任務全部完成時自動將階段標為完成。
- 甘特圖與 grid 逐列同步捲動。
- 進度歷史、趨勢或燃盡圖。
- 里程碑的進度。
- 舊發布快照與既有草稿的資料遷移。
- 窄螢幕的卡片式 grid。
- 外部交付表的改版。
- 後端 API 變更或 schema 驗證。

## Further Notes

- 「進度」「專案整體進度」已寫入 `CONTEXT.md`；詞彙表規定「階段是否完成由課長確認」，因此階段進度僅為資訊，不影響階段狀態。
- 不建議為本規格新增 ADR：每項決策都容易回頭修改，且沒有難以還原的代價。
- 建議的實作順序：純函式與測試 → 資料欄位與寫入白名單 → 甘特圖進度標示 → grid 取代卡片明細 → 階段「＋任務」與展開狀態 → 對照高亮 → 煙霧測試。
